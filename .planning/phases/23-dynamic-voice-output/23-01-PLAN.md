<action>
Phase-22 regression hotfix (R-1). Add `window.VoiceBus._liveAudio` to the barge-in guard so it only reacts to actual analyser readings, not to the fallback default level (`0.75` for `'speaking'`) emitted by `setState`. Without this, the `setState('speaking')` call inside `streamTTS` triggers a phantom level event that exceeds the `0.35` threshold, fires `bargeIn()`, calls `cancelAllAudio()`, aborts the in-flight `/api/tts` fetch, and silences all TTS output.
</action>
<acceptance_criteria>
- The barge-in check is `if (window.VoiceBus._liveAudio && window.VoiceBus.state === 'speaking' && effectiveLevel > threshold) bargeIn();`.
- A focused comment in the source explains the regression and why the guard exists.
- Deployed `/api/tts` returns 200 with valid MP3 (already verified pre-fix — server side was fine; the bug was client-side abort).
</acceptance_criteria>
</task>
